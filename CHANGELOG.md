# Changelog

Notable changes to the Ruvio server (`ruvio`, `ruvio-ctl`, the Docker image and the release binaries). New entries go under "Unreleased"; `scripts/release_version.py` moves them under the version number when the package is released.

## Unreleased

- `SCAN`, `HSCAN`, `SSCAN` and `ZSCAN` lower a `COUNT` above 10000 to 10000. One call runs on the shard's thread, so an unbounded `COUNT` held up every client of the shard; a scan that asked for more now needs more calls. Nothing changes for a `COUNT` of 10000 or less. The bounds are listed in the new `docs/LIMITS.md`.
- Persistence: WAL segments, snapshot files, the shard layout file and a data directory the server creates are now owner-only (`0600` files, `0700` directories) instead of following the process umask. Files and directories that already exist keep their mode. Nothing changes per command.
- ACL: an enabled user with no password hashes (for example after `ACL SETUSER default resetpass`, or a `user` line without `nopass` or a password) no longer accepts an empty `AUTH`, and new connections only log in as `default` without `AUTH` while `default` is `nopass`. Before, `resetpass` on `default` left the listener open to unauthenticated clients. Set `nopass` or a password on the user to log in. Nothing changes per command.
- Slot moves between groups: a replica that applied its primary's completed gain of a range and restarted before the coordinators sent the new cluster map no longer refuses to start ("cluster_topology gives slot … to another group, but this node holds its data"); it keeps the range and waits for the map. And a data node now refuses `RUVIO MIGRATE IMPORT` of a range while its background drop of the keys of that range (after giving it away or cancelling an import) is still running, answering `retry shortly`; before, that drop could remove keys of the new import. A range taken away by a map still needs the coordinators. No file or protocol format changed; nothing changes per command. Live restart test and a test of the refused import: not measured.
- Documented installing the prebuilt `ruvio-bin` package from the Arch User Repository (AUR) in the README and `docs/SETUP.md`.
- **Upgrading to this release:** (1) upgrade all `ruvio coordinator`s together: their Raft log format changed and a rolling upgrade stalls; (2) the replication handshake changed (versions 15-17): a primary and its replicas must run the same release, so a group is upgraded either by switching over to upgraded replicas (reads go on; writes pause for the replicas' restarts plus about `down_after_ms`) or by stopping the whole group; (3) WAL format minor 6 (new `SlotsArrived` record, logged by a target primary when it takes a range moved between groups): a node that took such a range after the upgrade cannot be started with an earlier release (it refuses the newer log segment); go back with the backup taken before the upgrade, or a fresh full copy. A replica of a development build from before this record that follows a newer primary refuses each such record and asks for a full copy, once per finished move; run primary and replicas on the same build; (4) the six client libraries now follow a failover by default (`follow_primary` and its equivalents, see `docs/CLIENT_BEHAVIOR.md` and each client's changelog); turn it off to keep the old behaviour. Upgrade the coordinators first, then the data nodes. Steps in `docs/COORDINATOR.md` (*Upgrading*, *Data nodes*) and `docs/RECOVERY.md` (*Upgrade*).
- Slot moves between groups: the end of an arriving range is now in the target primary's log (new WAL record `SlotsArrived`, format minor 6, logged on the receiving shard when the map gives the primary the range, before the primary records it), and the target's replicas take the range from it. Before, a replica took it only when the coordinators' map reached it, so a replica that was down while two moves into its group ran refused the second range and every newer map once back, and needed a full copy. A late cancel of a range no longer ends a newer range on another shard. A replica drops the copies of a cancelled range, and of a range its primary gave away, before it applies the next record (before, the drop ran in steps and could also drop the copies of a move of the same range that started right after), and drops a cancelled range's copies even when it never saw the range begin. Still not covered: a multi-shard replica down while moves into two of its shards run (each shard replicates on its own, so it may get the second range's start before the first range's end) and a replica that takes a full copy during a move; see `docs/COORDINATOR.md` (*Limits*). **WAL format minor 6: a release before this one cannot read a log that recorded a move between groups after the upgrade.** Primary and replicas run the same release, as before. Nothing changes per command.
- Cluster answers: a replica whose primary has not accepted it yet (just started or repointed with `REPLICAOF`, and its primary not reached yet) no longer lists itself as the master of its slots in `CLUSTER SLOTS`, `CLUSTER NODES` and `CLUSTER SHARDS`. With a cluster map it lists its group's primary from the map, then itself; without a map the answer is unchanged.
- `ruvio coordinator`: a data node configured as the group's primary that was restarted a second time after a failover no longer fences the real primary. Its last role was replica, so it forked a newer epoch on start; when the coordinators pointed it back it claimed that epoch, the real primary refused every write (`READONLY ... a replica has followed a newer epoch`) and the restarted node, which never followed, named itself the owner of the group's slots. The coordinators now send `REPLICAOF host port YIELD` (new Ruvio extension): the member claims no epoch while it follows the recorded primary and takes a full copy; the epoch on disk is not lowered. Plain `REPLICAOF` keeps fencing an older primary. A node of an older build gets plain `REPLICAOF`.
- `ruvio coordinator` rebalances slots: `COORDINATOR REBALANCE` on the leader evens out the slots across the groups, in proportion to their shard counts, as a sequence of slot moves of at most 256 slots each, run one after another on the existing move path, and answers how many moves it plans; `COORDINATOR REBALANCE DRYRUN` answers the plan (`first-last from/shard -> to/shard`) without moving anything. `COORDINATOR STATUS` adds `rebalance`, `rebalance_moves`, `rebalance_left` and `rebalance_error`; `COORDINATOR CANCEL` cancels the running move and ends the rebalance. Balance is by slot count, not keys or memory. The plan is not kept in Raft: after a leader change the new leader finishes the move in flight, and `COORDINATOR REBALANCE` on it goes on. Nothing changes on the data nodes' hot path or in any file or protocol format.
- Slot moves between groups: a replica of the target group could stop taking cluster maps for good when a second move to its group began before the coordinators' map for the first one reached it (it refused to record the second range while the first waited for a map, then refused every newer map because the second range's data was "not here"). The leader now sends the current map to the target group's replicas before each move (at most 1 s each), so moves can run back to back, as a rebalance does. A replica that is down during two such moves can still be left behind; `docs/COORDINATOR.md` (*Limits*) says how to recover it. Data nodes are unchanged.
- `ruvio coordinator` speaks TLS. New settings in `coordinator.toml`, all off by default: `tls_cert` and `tls_key` put the coordinator port (the Raft calls between coordinators and the Sentinel API) on TLS and make a coordinator call the others with TLS, so every coordinator needs them; `tls_ca` is the CA that vouches for the other coordinators' and, with `node_tls`, the data nodes' certificates; `node_tls = true` dials the data nodes with TLS (the coordinator shows its own `tls_cert` to a node that asks for a client certificate). Certificate files reload on the next connection after they change. The secret is still checked. Coordinators can now manage data nodes that take only TLS. With TLS off nothing changes; data nodes, clients and the hot path are unchanged. See "Security" in `docs/COORDINATOR.md`.
- All six clients retry `-TRYAGAIN` for 635 ms (7 retries, waits doubling from 5 ms) instead of 35 ms, long enough for the freeze of a slot move between groups; see each client's `CHANGELOG.md` and `docs/CLIENT_BEHAVIOR.md`.
- Slot moves between groups freeze the range for much less time: the source now waits for the target's replicas to hold the copy before it freezes the range (new `RUVIO MIGRATE REPLICAS id` on the target, at most 10 s; a target without it is not waited for), and the coordinators ask how the move is going every 10 ms instead of 50 ms, over one connection. Before, the leader waited after the freeze for the target's replicas to take the whole copy; with durability `always` a replica syncs it record by record, and in a local debug test a writer saw `TRYAGAIN` for 1.3-1.7 s, now 170-240 ms. Not measured on release builds. No file or protocol format changed; mixed versions keep working.
- `ruvio coordinator` starts a slot move again (up to three starts, as after a failover) when the source gave it up because the target did not prepare the frozen range within one second. Before, such a move ended as failed and needed another `COORDINATOR MOVE`.
- Client tests: every client now has a live test of a failover carried out by real coordinators. `scripts/run_with_servers.sh` also starts a group of two data nodes under three `ruvio coordinator` processes (`RUVIO_COORDINATOR_ADDRS`, `RUVIO_COORDINATOR_MASTER`, `RUVIO_COORDINATOR_GROUP_ADDRS`, `RUVIO_COORDINATOR_GROUP_PIDS`); each client's test kills the primary with SIGKILL and writes, at once, through a client with the coordinator option and one with the data nodes as seeds, until both reach the new primary. Measured on a Mac (debug server): through the coordinators about 0.9-1.6 s after the kill; with seeds about 5 s (Java) to 7.2 s (the others), because the seeds client lands on the replica, gets `READONLY`, and its rounds skip that node even after it is promoted. The tests allow 15 s. No client or server code changed.
- Docs: data-node upgrade runbook for groups under `ruvio coordinator`, checked with three data nodes and three coordinators as local processes (no write taken before the pause was lost; the promoted replica took writes 1.2 s after the primary stopped with `down_after_ms` 1000). `docs/COORDINATOR.md` *Primary lease* adds that a node answering a renewal later than 1 s misses that grant, with a `primary_lease_ms` of 3000-4000 for nodes that stall; `CLIENT DURABILITY` docs add that after a timeout the connection's next batch waits only if the shard logged a new record, so a read right after can see a write no replica holds yet.
- `CHANGES SUBSCRIBE` on a demoted primary: a stream open when the shard got `REPLICAOF host port` kept running, and once the shard's log was cut back to the fork and continued with the new primary's records, it streamed those records under the old generation; a consumer that later moved to the new primary was told to rewind only after it had applied them. The stream now ends with `["resync", "the shard follows another primary; resume on it"]` before any of the new primary's records, and the consumer subscribes on the new primary with its last cursor. Checked in the stream's own loop (role and epoch, already on the shard); nothing changes per command or for a server without streams. See `docs/CONFIGURATION.md` (*Change stream*).
- `ruvio coordinator` finds replicas the file does not list: the leader adds every replica the agreed primary lists in `INFO replication` and the group does not have yet (its replication address from the replica's `CONFIG GET replication-listen`), records the group's members in Raft, and watches, lists (`SENTINEL replicas`) and can promote them. New `COORDINATOR FORGET group host:port` on the leader drops a member and keeps it from being found again (not the primary, not one the file lists). Data nodes report a process identity, `run_id` in `INFO server` (as Redis does), so the coordinators do not add one node found under two addresses twice. Members are now known by their client address instead of their position in the file: the Raft record names the primary by address, and the coordinator-to-coordinator calls ask about a member by address. **The coordinators' Raft state changed again: a data directory written by an earlier development build of the coordinator cannot be read; delete `raft-log.json`, `raft-vote.json` and `raft-snapshot.json` and start all coordinators together.** See "Replicas the file does not list" in `docs/COORDINATOR.md`.
- `ruvio coordinator`: coordinators are added and removed while they run. New `COORDINATOR ADD id host:port` and `COORDINATOR REMOVE id` on the leader, and the setting `join` (default false) for a new coordinator that waits to be added instead of proposing its own membership. Majorities (failovers, the primary lease's coordinator count, `SENTINEL` `quorum` and `num-other-sentinels`, `SENTINEL sentinels`) now count the coordinators in the Raft record rather than `peers` in the file, which is only the first membership; a coordinator whose `peers` differ from the record logs a warning. `INFO` lists them as `coordinators:`. See "Adding and removing coordinators" in `docs/COORDINATOR.md`.
- `ruvio coordinator` `INFO` shows what the leader did and sees: `failovers_total` and `last_failover_unix_ms`, and per group `members_answering=n/m`, `state=ok|lease_running|waiting|no_candidate` with `state_ms`, and `lease_grant_ms` with the primary lease. A group waiting without a writer is warned about when it starts waiting and then at most every 10 s, instead of on every tick. See the coordinator section of `docs/OBSERVABILITY.md`.
- `ruvio coordinator`: a member is heard from only when every shard answers `ROLE` and `INFO replication`. Before, only shard 0 had to answer, so a multi-shard primary with another shard down (crashed, its port cut) was never failed over, and a replica with a shard down could be promoted. Now such a primary is failed over once `down_after_ms` passes without a complete answer, and such a replica is passed over. With the primary lease, a coordinator does not renew the lease of a primary with a shard it cannot reach, so the failover is not held up by a lease the old primary keeps renewing through its other shards. Coordinators ask each shard for `ROLE` once more per ping; nothing changes on the data nodes.
- `ruvio coordinator`: the leader confirms with a majority of coordinators before every command it sends a data node, not only at the start of each tick (a confirmation is still trusted for one `ping_interval_ms`, at most 1 s), so a leader that loses its majority in the middle of a tick no longer points members at a primary a newer leader replaced. Each group is now tended on its own task, and a member gets `down_after_ms` (at least 1 s) to answer a command instead of 10 s: a member that accepts connections but stops answering no longer holds up a failover in another group (measured on a Mac, debug build, `down_after_ms` 1000: the other group's replica took over 1.3 s after its primary was killed, against 9.6 s before). Nothing changes on the data nodes.
- Multi-shard shutdown with a failed shard log: the failed shard hands the final checkpoint round a copy of its last published file, and could hand it a second one after that round was already published, starting a new round no shard completed. Its directory (a full copy of the shard file) was left in `checkpoints/` until two later rounds published. No round starts after the final round is published now. No file format changed.
- `ruvio coordinator`: optional primary lease (issue #108). An old primary cut off from the coordinators together with one of its replicas kept `min-replicas-to-write 1` satisfied and took writes for the whole partition. With `primary_lease_ms` on the coordinators (default 0, off; `primary_lease_drift_percent` default 10, below 100: how much faster or slower than real time any clock may run, a coordinator counting a lease ended after it times (100 + d) / (100 - d) plus 200 ms) and `primary-lease yes` on the data nodes (`replication.primary_lease`, `RUVIO_PRIMARY_LEASE`, `CONFIG SET`; default off), each coordinator renews the agreed primary's lease every ping interval, each group on its own task (new `RUVIO LEASE BEGIN`/`GRANT`, `@admin @dangerous`), a writer refuses writes with `NOREPLICAS Primary lease expired: too few coordinators renewed it.` unless grants from a majority run for more than 300 ms more (measured with `CLOCK_BOOTTIME` on Linux, so a suspended host wakes with its lease expired), and a failover (and `COORDINATOR FAILOVER FORCE`) waits until a majority of coordinators report the lease ended by their own settings; each of them then grants that member again only after the leader confirms, after any failover it is deciding, that its record still names it (a confirmation waits only for a decision about its own group). A node counts the majority against the largest coordinator count (at most 255) a running grant of the current epoch names, and forgets grants that ended, so coordinators that start over at a lower epoch are taken at most one lease later. The window shrinks from the whole partition to at most the lease; writes taken in it are still lost. The check runs on the existing 100 ms tick: nothing is added per command, and with the setting off the tick reads one flag. `INFO replication` gains `primary_lease`, `primary_lease_grants` and `primary_lease_remaining_ms`. Turning it on needs every coordinator on this version (new coordinator-to-coordinator calls report and confirm the lease; older coordinators neither grant nor answer them, so failovers wait for a majority that does; with the lease off a newer leader falls back to the older call): upgrade the nodes, then all coordinators together, set it on the coordinators, and turn it on at the nodes last; turn it off on the nodes first. Clients need no change. Docs: `docs/COORDINATOR.md` now states the split-brain bound without the lease (only `min-replicas-to-write` equal to the number of replicas bounds this shape, and `CLIENT DURABILITY REPLICAS 1` can lose acknowledged writes in it) and has a table of failure shapes and what each can lose.
- `ruvio coordinator` records the committed sequences a failover must keep in Raft (issue #107): the leader writes the shards that rose at most once a second, in one entry for all groups, and decides at each promotion which values still hold (recorded with the promotion). A new leader acts only after it applied the log of its term. So a new leader, or coordinators that all restarted while the primary was down, no longer promote a replica missing acknowledged `CLIENT DURABILITY` writes. Coordinators' `INFO` adds `recorded=` per group. The coordinators snapshot their log every 100 entries instead of 5000. **The coordinators' Raft log format changed: upgrade all coordinators together** (a rolling upgrade stalls; going back means deleting the coordinators' Raft files, see `docs/COORDINATOR.md`). Data nodes, clients and the hot path are unchanged.
- Output limit: a pipeline whose client was reading its replies could still be cut with `-ERR output buffer limit exceeded`, its last replies dropped, when the replies queued since the last send crossed `max_output_buffer_bytes` before the next send (more likely with large replies, or a limit under 128 KiB, where nothing was sent before the limit). A pipeline now sends what the socket takes by the time half the limit is unsent, so only bytes the client has not taken count, as documented; a single reply larger than the limit is still refused.
- `ruvio coordinator`: a leader cut off from the other coordinators stops acting on the data nodes (issue #106). The Raft library does not step down a leader that lost its majority, so the leader now confirms with a majority (one heartbeat round per tick, at most one `ping_interval_ms`, capped at 1 s) before failovers, `REPLICAOF` corrections, cluster map pushes, slot move steps and `COORDINATOR FAILOVER FORCE`/`MOVE`/`CANCEL`; until it can, it logs one warning and does nothing to them. See `docs/COORDINATOR.md`.
- Docs: how `IDEM`, `ONCE`, `LIMIT` and `LEASE` behave across a failover (use `CLIENT DURABILITY REPLICAS 1` on the writing connection, keep clocks synchronized, a failover-safe lock recipe with fenced tokens); see `docs/IDEM.md`.
- `CHANGES SUBSCRIBE` cursors survive a failover (issue #24): a cursor is now `<generation>:<shard>:<seq>`, the generation being the shard's replication epoch, and events, heartbeats, the subscribe reply and the `moved` value of a range moved between a server's own shards use that form. The old `<shard>:<seq>` form is still accepted, read as the current generation. On a promoted replica, a cursor of the old primary's generation at or before the fork resumes as before; one past it gets one `["rewound", cursor]` push naming the fork, then the stream continues from there, and the client undoes or reloads what it applied after it. A cursor of a newer generation, or of one older than the shard forked from, is refused. New `COMMITTED` option: only records at or below `replication_committed_sequence` are streamed, so no event is taken back by a failover; it is refused on a shard that does not replicate, and delivers nothing new while no client uses `CLIENT DURABILITY`. A demoted primary now forgets its committed sequence. No file format changed: the generation and the fork come from the existing `LINEAGE_####` files. See `docs/CONFIGURATION.md` (*Change stream*).
- Very large expirations (issues #94, #101): a relative expiration whose deadline does not fit a signed 64-bit millisecond clock (`SET k v PX 9223372036854775807`, `EX 9223372036854775`, `PEXPIRE`, `PSETEX`, `EXPIRE`, TTL on create, `FILLSET`, `IDEM`, `RESTORE`) is refused with `invalid expire time`, as Redis does. Before, it was stored, `TTL` panicked a debug build (a release build wrapped to a negative number) and `PEXPIRETIME` answered a negative number. `EXPIREAT` and `SET PXAT` up to the largest value are still accepted. `LEASE`, `SEMAPHORE`, `RENEW`, `ONCE` and `GETEX` have no error reply; their very large deadlines are now reported without overflow by `TTL`, `PTTL` and `PEXPIRETIME`. Nothing changes on the path of other commands.
- `ruvio coordinator` keeps `CLIENT DURABILITY` writes across a failover (issue #24): it reads each member's `replication_committed_sequence` with the `INFO replication` it already sends, and promotes only a replica that holds, in every shard, the highest committed sequence seen for the group. When none does, the group waits without a writer and the leader logs a warning on every tick. New coordinator setting `unclean_failover` (default false) promotes the best replica anyway, and new `COORDINATOR FAILOVER group FORCE` on the leader does it once; both lose the records the replica lacks. The coordinators' `INFO` shows the known values as `committed=` on the group's line. Groups that never use durability fail over as before. See `docs/COORDINATOR.md`.
- New `CLIENT DURABILITY REPLICAS n [TIMEOUT ms]` (issue #24): a connection's replies leave only once `n` replicas hold the records written before them on disk (default timeout 5000 ms; `REPLICAS 0` turns it off). The primary syncs its log at once instead of on the next `everysec` tick, and its replicas sync and acknowledge every batch while someone waits. On timeout every reply of that batch becomes `-NOREPLICAS Not enough good replicas to write.`; the writes stay applied, as with `WAIT`. Refused inside `MULTI` and on a server without replication. A connection that does not ask pays nothing (one check per reply flush). Replicas show the primary's committed sequence in `INFO` (`replication_committed_sequence`). Measured locally in debug: a durable `SET` with one replica on the same machine took about 26-28 ms; not measured on real machines. All six clients have the command and a connect option that sends it on every connection. **The replication handshake changed (versions 15-17): primary and replicas must be upgraded together.** See `docs/COORDINATOR.md` and `docs/COMPATIBILITY.md`.
- `INCRBYFLOAT` and `HINCRBYFLOAT` (issue #95): the result is rounded to 16 significant digits instead of 15 (`0.1 + 0.2` still prints `0.3`, as in Redis), so more of a large counter survives, e.g. `12345678901234.5` plus `0.01` now gives `12345678901234.51`. The rounded text is still what is stored, so digits beyond the 16th are lost and very small increments can still vanish; `docs/COMPATIBILITY.md` now says so and points to `INCRBY`, `TAKE` and `TRANSFER` for money. Clients' doc comments say 16 digits.
- **Behaviour change:** `LEASE` and `SEMAPHORE` tokens are fenced (issue #96): a token is larger than every token an earlier holder of the key got, also after the key expired or was deleted, after a restart, a failover or a slot move to another group. `LEASE` tokens no longer count 1, 2, 3 per key and no longer restart at 1 after `DEL`. The token is `generation << 48 | counter`: the generation is the replication epoch, or the cluster map version a coordinator raises on every failover and committed move; the counter has a clock floor (milliseconds × 64). A semaphore that exists at the upgrade keeps counting from its saved token; new semaphores start lower than the old clock-based tokens did. The reply is still one integer; treat it as an opaque 64-bit value. No log format change; nothing on the path of other commands.
- Slot ranges move between groups of a multi-node cluster (issue #23): `COORDINATOR MOVE first last group shard` on the coordinators' leader moves the range to that shard of `group` while both keep serving it; `COORDINATOR STATUS` and `COORDINATOR CANCEL` follow and stop it. The source node copies the range to the target over its client port (`RUVIO MIGRATE`, `@admin @dangerous`), then freezes it for the last changes: its commands get `TRYAGAIN` until the coordinators commit the move and send a newer map, after which the source answers `MOVED` and drops its copy in bounded steps. Replicas of both groups follow from the log (new `SlotsIncoming` and `SlotsGiven` records, WAL format minor 5), a prepared move survives restarts of both nodes, and a failover before the commit cancels and restarts it. A node now accepts a map that changes its own slots, but refuses one that gives it a slot whose data is not there. New setting `migration_max_bytes_per_sec` (default 0, no cap) limits a source's copy rate. Nothing changes for a cluster that moves nothing. See `docs/COORDINATOR.md`.
- Multi-node cluster (issue #22, first step): `cluster_topology` names a map that gives every hash slot to one group (a primary and its replicas) and `cluster_group` this node's group. A node serves its group's slots, split evenly over its shards, and answers `-MOVED slot host:port` for every other slot (inside `MULTI` the transaction is aborted); `CLUSTER SLOTS`, `SHARDS`, `NODES` and `INFO` describe the whole map. The map is read at startup and fixed; data is not moved between groups yet. A node that holds keys of slots the map serves elsewhere refuses to start. With `ruvio coordinator`, give each group `shards` and `slots` in `coordinator.toml`: the coordinators send every node the map (new `RUVIO TOPOLOGY SET`/`VERSION`, `@admin @dangerous`), named by each group's agreed primary, after every failover; a node keeps the newest in `TOPOLOGY` in its data directory. A one-shard node with a map runs as a one-shard cluster. Nothing changes without a map. See `cluster_topology` in `docs/CONFIGURATION.md` and `docs/COORDINATOR.md`.
- New `RUVIO MOVESLOTS first-last shard` and `RUVIO MOVESLOTS STATUS` (`@admin @dangerous`): move a slot range to another shard of the same server while both keep serving it, to take load off a busy shard. The source copies the range in bounded steps, sends the keys written meanwhile again, and hands over in one step that pauses the source shard briefly (measured on a Mac with 200,000 keys in one slot: about 0.06 ms at the median and at most 1.5 ms in `memory` mode, 13-18 ms in `everysec` and `always`, almost all of it the target's log sync and writing the slot table); then it drops its copy. Clients still routing to the old shard are forwarded; no `MOVED`. One move at a time; refused while replication is on and in `snapshot` durability. With a log, the move survives a crash at any step: the new `SLOTS` file in the data directory records the moves, and recovery keeps, per slot, only what each shard held while it owned it. Copies are logged as a new WAL record (`SlotCopy`), and the old owner's `CHANGES` stream gets a `moved` event naming the cursor where the new owner continues. **The WAL format minor is now 4:** a server that moved slots writes logs an older release cannot read. All six clients have `move_slots` and `move_slots_status` (`MoveSlotsAsync`/`GetMoveSlotsStatusAsync` in C#). See `docs/COMPATIBILITY.md` and `docs/RECOVERY.md`.
- `HMSET` (issue #26): multi-field `HSET` that replies `OK`, as Redis does; PHP cache handlers such as CodeIgniter 4's send it through phpredis. New [docs/PHP.md](docs/PHP.md): phpredis and Predis, checked against Ruvio, with CodeIgniter 4 and Laravel cache and session notes. The six clients have a typed `HMSET` method.
- Recovery memory (issue #71): after a crash the WAL records replayed since the last checkpoint were kept for the life of the shard, so a restart used 2-3x the memory of the same data and a memory-limited pod could crash-loop. Each record is now dropped once applied and the freed pages are returned. Measured with 1M keys of 64 B, `everysec`, SIGKILL and restart: RSS 286 MB before, 102 MB after (95 MB before the kill).
- `hot_keys` (issue #52): a hot `SET`/`DEL` (and `FLUSHDB`/`FLUSHALL` on hot keys) is now logged before the shared hot store changes, so a write the WAL refuses (a failed log, an oversized record) is no longer readable by other clients until a restart. The record is written to disk just after the store's lock is released, as a grouped shard write is: a disk error there answers `MISCONF`, and the log keeps the record and writes it when it resumes. The exception note in CONFIGURATION.md and the README is gone. Measured with 2 shards: hot `SET` throughput unchanged (`everysec` 1.02x, pipelined 0.98x, `always` 1.05x of before).
- WAL (issue #32): a segment longer than `wal_segment_bytes` (written before the setting was lowered, or above `ruvio-ctl`'s 256 MiB default) is read with a warning instead of being reported as corrupt, so startup, `ruvio-ctl check/inspect/backup/restore` work on such a data directory.
- ACL (issue #38): a `+parent|sub` / `-parent|sub` rule must name a subcommand Ruvio checks (`config|get`, `acl|setuser`, `client|kill`, ...); any other is refused. Such a rule could never match a command, and each distinct name was kept in memory for the life of the process.
- `EVAL`, `EVALSHA`, `FCALL` and `PUBLISH` can be queued in `MULTI` (they aborted the transaction before). Scripts run in their place at `EXEC` and their writes join the transaction's WAL record; a queued `PUBLISH` is sent after `EXEC` is recorded, so `DISCARD` or a refused write sends nothing. `SELECT` stays refused inside `MULTI` (issue #41).
- Client tracking table (issue #43): the readers of a tracked key are kept inline when there is one (no allocation), in a small vector up to 32, and in a set above that, so a connection leaving no longer scans every other reader of a hot key (O(N²) before) and the common one-reader key uses less memory. Measured on 1M tracked keys: 238 → 190 bytes per key with one reader (-20%), 310 → 288 with two, about the same at four, 796 → 757 at twelve. Tracking off still costs nothing.
- Docker image (issue #46): new `ruvio-ctl ping [--address A] [--connect-only]` (exit 0 when the server answers; `NOAUTH` counts), used by a `HEALTHCHECK` in `Dockerfile` and `Dockerfile.linux`; the builder and runtime base images are pinned by digest, and `.github/dependabot.yml` keeps the digests current weekly.
- Docs: `clients/java/README.md` said 287 commands (the matrix has 296); the compatibility check now also catches a capital "All N commands", and `clients/README.md` explains why `clients/testdata/commands.json` has fewer entries (it lists command names, the matrix lists subcommands separately) and that `ruvio-ui` is not a client (issue #47).
- `ruvio import --replace` now writes each key under a temporary key and renames it over the target's, so a crash no longer leaves a half-written key or one without its TTL (issue #29). See `docs/IMPORT.md`.
- The HTTP `/metrics` endpoint is not served by the server (the setting was accepted but nothing listened). It is removed from the docs, `deploy/kubernetes.yaml` and `deploy/ruvio.toml`; metrics are read with `INFO prometheus`. The server logs a warning at startup when `metrics_address` is set. An HTTP endpoint may come later.
- `SCAN cursor … SLOT n` returns only the keys of hash slot `n`, from any port of a multi-shard server (it runs on the shard that owns the slot). `COUNT` still bounds each call. No memory is added per key.
- New `ruvio coordinator`: automatic failover. Three or five coordinators (a separate mode of the same binary; no data, no data commands) agree through Raft on each replication group's primary, fail it over when a majority cannot reach it (`REPLICAOF NO ONE` on the replica holding the most history, the others pointed at it), and make an old primary a replica when it returns. They answer the Redis Sentinel API subset clients use (`SENTINEL get-master-addr-by-name`, `masters`, `replicas`, `+switch-master`), so clients with Sentinel support follow a failover. Shared `secret` for coordinator calls and `AUTH`. Built with the default `coordinator` Cargo feature (openraft 0.9.25). See docs/COORDINATOR.md and deploy/compose.failover.yml.
- A replica that follows its primary by host name now tries every address the name resolves to; `localhost` resolving to ::1 first no longer keeps it from a primary listening on 127.0.0.1.
- Reads from replicas. A replica now tells its primary where clients reach it (`advertised_host`, and `advertised_port` or the bind port plus the shard index; a replica that announces a loopback host from another machine is listed at the address it connected from). Once it has finished copying, the primary lists it after its own shard in `CLUSTER SLOTS`, `CLUSTER SHARDS` and `CLUSTER NODES`, in `ROLE`, and as `slave0:ip=…,port=…,state=online,offset=…,lag=…` lines in `INFO replication`. A replica answers the cluster commands with its primary first, so a client seeded with a replica sends writes to the primary. New `replication.announced` (`RUVIO_REPLICA_ANNOUNCED`, `CONFIG GET replica-announced`, default on) keeps a replica out of these answers. Node ids are now the SHA-1 of the announced `host:port` instead of the shard number. All six clients get a read policy (primary by default, prefer-replica, replica); see `docs/CLIENT_BEHAVIOR.md`. A replica no longer acknowledges while it installs a full copy and catches up, so `WAIT` and `min-replicas-to-write` stop counting it until its copy is complete (before, it acknowledged the log it was replacing). The replication handshake changed again: primary and replicas must be upgraded together.
- New opt-in TLS for the replication link (issue #37): `replication.tls = true`, `replication.tls_ca` (replica), optional `replication.tls_client_cert`/`tls_client_key`; the primary reuses `tls_cert`/`tls_key`. Off by default, with no change to the stream and nothing loaded when off. The startup warning no longer appears once it is on. See `docs/CONFIGURATION.md`.
- Fixes: `XADD *` on a stream whose last sequence is the largest possible now continues at the next millisecond instead of failing with an invalid ID; `LIMIT` with a maximum above `i64::MAX` reports a remaining count of `i64::MAX` instead of a negative number; a replica whose primary address plus shard number passes port 65535 now reports a configuration error instead of dialling a wrong low port.
- Deployment files: `deploy/kubernetes.yaml` now uses the current image tag, no longer ships a placeholder password (create the secret with `kubectl create secret`, see the comment at the top) and runs as user 10001 with a read-only root file system, no capabilities, `fsGroup` for the volume and a memory limit; `deploy/ruvio.service` gets `StateDirectory=ruvio` (the data directory is created and owned by the service) and sandboxing options; `deploy/ruvio.toml` no longer sets `requirepass = "change-me"`; the Dockerfiles stop copying a config file the image never read; `docs/SETUP.md` points at the current release, and `scripts/check_package_metadata.py` now fails when a download line or the Kubernetes image tag differs from `Cargo.toml`.
- The server now logs a warning at startup when TLS is on and replication listens on, or dials, another machine: TLS covers client connections only, and the replication stream (including its password) is not encrypted. `docs/CONFIGURATION.md` and `docs/THREAT_MODEL.md` say so. TLS for the replication port itself is not done yet (issue #37).
- `ruvio import` hardening: the reply reader refuses bulk strings above 512 MiB, arrays above 64M items and nesting deeper than 32 instead of allocating or recursing without bound; an error reply to the `EXISTS` check on the target now stops the import instead of being read as "key absent" (which could overwrite the target's key); with `--replace`, a key that vanished from the source between the probe and the copy is counted as vanished and the target's copy is no longer deleted; the key's TTL is read again after the copy, so it no longer includes the copy time.
- Durability fixes: `SHARD_LAYOUT` is written through a temporary file and renamed, so a crash while it is created can no longer leave a partial file that blocks every later start; `ruvio-ctl backup` flushes the copied files, the signature and the directories to disk before it reports success; a certificate reload that fails (a half-rotated pair, a half-written file) now keeps serving the previous certificate, logs a warning and is not retried until a file changes, instead of failing every new TLS connection.
- New `REPLICAOF host port`, `REPLICAOF NO ONE [FORCE]` and `ROLE`: a replica is promoted, and a primary or replica is pointed at another primary, without a restart, on every shard at once. A promoted shard keeps its replicas' logs usable (see the lineage entry). A primary that a replica of its successor connects to stops taking writes (`READONLY`, `INFO replication_fenced`), and `INFO` shows `replication_epoch`. New `min-replicas-to-write` and `min-replicas-max-lag` (Redis semantics, off by default, changeable with `CONFIG SET`): a primary refuses writes with `NOREPLICAS` while too few replicas acknowledge; replicas now repeat their acknowledgement every second while idle.
- Promoting a replica no longer makes every other replica take a full copy. The promoted shard records the history it followed and where it forked (`LINEAGE_####` per shard); a replica that stopped at or before that point continues from its own log. An epoch that grows with every promotion makes a replica refuse a replaced primary and a replaced primary refuse such a replica. The replication handshake changed: primary and replicas must be upgraded together, as before.
- New `CONFIG SET name value [name value ...]` and `CONFIG REWRITE`. `CONFIG SET` changes the memory (`maxmemory`, `maxmemory-policy`, compact thresholds, `notify-keyspace-events`), slowlog and key-statistics, connection (timeouts, connection limits, `max-commands-per-second`, `max-output-buffer-bytes`), script and `requirepass` settings while the server runs; every shard applies the change before `OK`. A restart-only, unknown or invalid name fails the whole call and changes nothing. Connection settings apply to new connections. Nothing is logged or replicated. `CONFIG REWRITE` writes the live values into the config file the server started from. `docs/CONFIGURATION.md` and the site's configuration page show for each setting whether it changes while running and under which `CONFIG SET` name. All six clients have `config_set` and `config_rewrite` (`SetConfigAsync`/`RewriteConfigAsync` in C#).
- **Behaviour change:** an ACL user granted `+config` (or `+@admin`) could only run `CONFIG GET` before; it can now also run `CONFIG SET` and `CONFIG REWRITE`, as in Redis. Give read-only users `+config|get`, or add `-config|set -config|rewrite`.
- All six clients accept a list of seed addresses next to the single host and port. Connecting tries them in order; after a dropped connection a standalone client reconnects starting with the next seed, and a cluster client reloads `CLUSTER SLOTS` from another known node or seed before giving up. No server change; the rules are in `docs/CLIENT_BEHAVIOR.md`.
- New `RENEW key token ttl_ms`: extends a `LEASE` or `SEMAPHORE` holder by its token (1 when the token is a live holder, 0 otherwise) without releasing it, so a long job keeps its slot and its fencing token. All six clients have `renew`; lease and permit handles gain `renew` where they exist.
- TTL on create: `INCR`, `DECR`, `INCRBY`, `DECRBY`, `INCRBYFLOAT`, `HINCRBY`, `ZADD`, `ZINCRBY`, `GEOADD`, `XADD`, `SETBIT`, `JSON.SET` and `BF.INSERT` take `EX seconds` or `PX milliseconds`. The deadline is set only when the call creates the key; an existing key keeps its deadline. The write and the deadline are one WAL record, so a crash never leaves the key without its TTL.
- `EXPIRE`, `PEXPIRE`, `EXPIREAT` and `PEXPIREAT` accept `NX`, `XX`, `GT` or `LT`. `SADD`, `LPUSH` and the other variadic writes use `EXPIRE key ttl NX` in the same pipeline or `MULTI`.
- New `ZPOPBYSCORE key max [MIN min] [COUNT n] [WITHSCORES]` and `ZMOVEDUE source destination max [COUNT n]`: take the due members of a sorted set (score up to `max`) and return them, or move them to the tail of a list, in one command. At most 10000 members per call.
- New: `SET key value IFGT|IFLT [EX|PX|EXAT|PXAT|KEEPTTL]` writes an integer only when the key is missing or the number is greater (`IFGT`) or smaller (`IFLT`) than the stored one, so a watermark, version or best price needs no script. It answers `OK` or a null bulk; a non-integer argument or stored string is an error and writes nothing. Typed options in all six clients.
- New `TRANSFER source destination amount [MAX cap]` and `HTRANSFER key from to amount [MAX cap]`: move an integer amount between two keys (same slot) or two fields of a hash only when the source holds enough, in one WAL record. Reply `[source, destination]` after, or a null bulk and no write.

- `LIMIT key max window_ms SLIDING` counts with a weighted two-window estimate, and `LIMIT key capacity refill_ms TOKENS [COST n]` is a token bucket. Both keep a few bytes per key, write nothing when they refuse, and take `WITHRETRY` to reply `[remaining, retry_after_ms]`. Plain `LIMIT key max window_ms` is unchanged, and the new modes use the existing limit records, so the WAL and snapshot formats do not change.

## 0.3.3 - 2026-10-17

- **Behaviour change:** `port_mode = "per-shard"` is now the default. A multi-shard server also listens on port+1 .. port+N-1, one port per shard; `single` is deprecated. A key sent to the wrong shard's port is forwarded to its owner instead of answered with `MOVED` (`SSUBSCRIBE` and `SPUBLISH` still answer `MOVED`).
- **Behaviour change:** in per-shard mode `FLUSHDB` empties only the shard it is sent to, like Redis Cluster; a plain client on one port sees only that shard for `KEYS`, `DBSIZE`, `SCAN` and `FLUSHALL`.
- `PUBLISH` reaches subscribers on every shard without waiting for them. Each shard's fan-out is bounded (16384 messages or 64 MiB); messages over the bound are dropped and counted in `INFO` as `pubsub_cluster_dropped`. The reply counts the local subscribers. `PUBLISH` inside `MULTI` is refused on a multi-shard server.
- `WAIT` also waits for the replicas of the shards a connection's writes were forwarded to.
- More writes share one WAL group write (`INCRBYFLOAT`, `SETRANGE`, `BITFIELD`, `COPY`, `LSET`, `LMOVE`), and an `SADD` that adds nothing writes no WAL record. `SLOWLOG` times commands with the CPU cycle counter.
- `RUVIO_WAL_PREFILL=auto|on|off` controls zero-filling of new WAL segments.
- Fixed: ACL rules naming a subcommand allocated a new copy of the name each time.
- Fixed: on Windows, backup, restore and replication failed to flush files opened read-only.
- Fixed: a replication port past 65535 (listen port plus shard number) wrapped around to an unrelated port instead of being refused.
- Fixed: on macOS a blocked client that hung up behind unread input was not noticed until its timeout.
